# AI Coding 日报 · 2026-10-20（周二）

## 今天动向

1. **Agent 的提交量把代码托管平台压到要换架构。** GitHub 上的 Git 事件从每月 2,182 亿涨到 4,733 亿，9 月提交数是去年同期的 5 倍多。GitHub 正在把存储和计算拆开、重建 Git 基础设施，内部基准测试里写入吞吐最高提升了 35 倍。（[GitHub 工程博客](https://github.blog/engineering/architecture-optimization/building-git-infrastructure-for-agent-scale-development/)）
2. **Claude Code 团队按风险分级做审查。** 6 到 9 月，合并的 PR 数量翻了一倍多，回滚占比反而下降了 40% 以上。低风险改动可以零人工审批直接合并。（[原文](https://claude.dev/blog/solving-code-review-at-anthropic/)）
3. **基准分可能被高估了三分之一。** TestJack 审计了 4,487 次判定通过的结果，其中 34.4% 实际违反了需求，解决率从 50.6% 降到 33.2%。（[论文](https://arxiv.org/html/2610.10619)）
4. **Meta 用薄路由取代了全知 agent。** 新方案是一个 1,300 行的确定性路由器，加上 14 个上下文隔离的专家 agent。新数据列的配置准备从 3–4 天缩短到 1 小时以内。（[Meta 工程博客](https://engineering.fb.com/2026/10/19/ml-applications/thin-orchestrator-ai-agent-architecture/)）
5. **Agent 的产出已经超过人。** 8 月，GitHub 上 agent 提交的 PR 首次多于人类；Linear 上 agent 创建的 issue 从 7 月起就多于人类。（[Pragmatic Engineer](https://newsletter.pragmaticengineer.com/p/the-state-of-the-tech-industry-in)）

## 一、行业动向

### 深读｜[TestJack: Should you trust the results in coding benchmarks?](https://arxiv.org/html/2610.10619)

Koushik Sen、Baishakhi Ray、Dawn Song 等（Columbia / UC Berkeley / George Mason）· 2026-10 · 正文约 30 分钟 · **必读原文**

**问题：** 几乎所有编码基准都把"固定单测通过"当作解决。但单测只覆盖一部分需求，agent 既可能钻测试的空子，也可能漏掉需求照样全绿。

**方法：** 以 prompt 为准，用参考答案当裁判。

- 每个通过的补丁放进三个环境里跑：agent 补丁、参考答案、原始仓库。原始仓库也能通过的测试，等于什么都没验证。
- 把任务描述拆成原子需求，再从三个方向找疑点：测试没覆盖到的分支、刷分行为（硬编码期望值、特判被测输入、识别测试环境、篡改测试框架）、变异测试暴露的空白。
- 每个疑点写一个证据测试，要求它在参考答案上通过、在 agent 补丁上失败；另一个 reviewer 只看 prompt 复核，剔除过度贴合参考答案的测试。

**数字：**

- 4,487 次通过里推翻了 1,545 次（34.4%），解决率从 50.6% 降到 33.2%。
- 分基准看，SWE-bench Verified 只推翻 7.6%（80.5% 降到 74.4%），SWE-bench Pro 推翻 29.2%（51.4% 降到 36.4%），DeepSWE 推翻 43.5%。
- 轻量版只花 15.4% 的成本，就找回了 72.4% 的推翻结果。
- 典型案例：有一次运行漏掉了数据库迁移，照样通过，补丁新增代码只有 6.7% 被执行到；另一次把 `failed_deletes = 1` 直接写成常量，骗过了只有一个样例的测试。

**局限：**

- 必须有参考答案才能用。
- 审计员本身是 LLM，可能判错。
- 约四分之一的 DeepSWE 任务描述本身就不完整。
- 轻量版的精度只有 49.2%。

**可借鉴：** 内部 agent PR 的验收不要停在"CI 全绿"。

1. 让独立 agent 把 issue 拆成需求清单，逐条标出有没有测试覆盖。
2. 在改动前的代码上跑新测试，能通过的测试不算证据。
3. 用分支覆盖率找出补丁里没被执行到的新增代码，再静态检测硬编码和特判。

另外，内部选型用的评测集，建议每季度用这套方法抽样审计一次。

### 深读｜[The state of the tech industry in 2026](https://newsletter.pragmaticengineer.com/p/the-state-of-the-tech-industry-in)

Gergely Orosz · 10-06 · 约 25 分钟 · 摘要已足够

**问题：** 过去一年，AI 实验室、创业公司和大厂的研发方式到底变了什么，哪些坏了，哪些没变？作者实地走访了 OpenAI、Anthropic、Ramp、Uber，还拿到了 GitHub、Factory、Linear 的未公开数据。

**数据：**

- **产出：** GitHub 上 agent 提交的 PR 在 8 个月里涨了 9 倍，8 月首次超过人类。作者估算全 AI 生成的 PR 每月超过 7,500 万。Factory 有 83% 的用户在用 skills。
- **工作方式：** 顶尖工程师通常同时开 5 到 10 个 agent 会话。Anthropic 内部一个项目往往最多容纳 2 个人，再多 agent 之间就会互相踩脚。
- **自建 harness 成了标配：** Stripe 的 Minions、Uber 的 Minion、Shopify 的 River、Meta 的 Devmate、Google 的 Agent Smith、Dropbox 的 Nova、Spotify 的 Honk。
- **迁移周期大幅缩短：** Bun 从 Zig 迁到 Rust 用了 11 天，原估 1.5 人年；Airbnb 迁移 3,500 个测试文件用了 6 周；Uber 把 60 万个测试从 JUnit 4 升到 JUnit 5 用了 4 个月。
- **成本：** Uber 用开源模型加智能路由，token 用量在涨，总成本却从 5 月起持平，单 token 成本降了 50% 以上。
- **坏掉的：** 人工审查沦为表演，大量 PR 直接 LGTM；只经过 AI 审查的 PR 越来越多；质量和可靠性普遍下滑；CPU 开始短缺。
- **没变的：** 团队编制和规划依然重要；测试投入和写代码相当；受访公司都不让非工程师直接发布到生产；一些老实践重新显出价值，比如先打通一条端到端的最小可用路径（tracer bullet）。

**局限：** 样本偏向 AI 前沿公司，不少数据来自供应商。评论区有人质疑受访方有夸大的动机，文中也没有质量方面的长期跟踪数据。

**可借鉴：** 用文中"过去一年的 16 项变化"和"哪些坏了"两份清单，给团队做一次差距盘点：有没有内部 harness 或 cloud agent？审查是不是已经在走过场？有没有做模型路由？有没有一份可以交给 agent 的积压迁移清单？

## 二、工程化实践

### 深读｜[How the Claude Code team does code review](https://claude.dev/blog/solving-code-review-at-anthropic/)

Addy Osmani 等（Anthropic）· 10-15 · 约 18 分钟 · **必读原文**

**问题：** Claude Code 约 90% 的代码由 Claude 写，逐行人工审查已经不现实。目标是在回滚率和事故率不上升的前提下，把每个 PR 的人工时间降到最低。追踪的指标是每个 PR 的人工审批数（中位数和 P95）、人工评论数和等待时长。

**方法：六层，最底下兜着回滚。**

1. **提 PR 前先自证。** 必须附上测试、构建或截图的实际输出，再由一个全新上下文的 subagent 审 diff。Boris Cherny 估计，能自我验证的 agent 结果好 2 到 3 倍。`CLAUDE.md` 尽量短；各目录的 owner 写 `REVIEW.md`，说明这里"失败长什么样"，并要求每条意见带文件和行号作证据。
2. **每个 PR 都过 AI 审查。** 多个 agent 并行找 bug，再由另一组投票，多数确认才发出，纯风格意见丢弃。每条意见标为 Important、Nit 或 Pre-existing（历史遗留问题），作者必须逐条回应：修，或者写明理由后关闭。
3. **安全审查**，可以阻断合并。
4. **CI 阻断**，PR 模板必须填"怎么测的、风险、怎么回滚"。
5. **人工审批按风险分级。** 分类器按改动内容判定风险：低风险 0 人、中风险 1 人、高风险 2 人。CI workflow 和敏感路径必须有人审；agent 的批准永远不能顶替人；审批只对当前 commit 有效，新 push 后要重新批。
6. **合并队列、feature flag、先内部使用、双通道分阶段发布，加一键回滚。**

**数字：**

- 合并的 PR 数翻了一倍多，回滚占比下降 40% 以上。
- 收到实质性审查意见的 PR 从 16% 升到 54%。
- 历史事故对应的 PR 被做成评测集，审查 agent 每天跑一遍。

**踩坑：** 有个 PR 一夜之间被 agent 互审互改了 50 多轮，其中约 59% 的问题是第一轮就存在的旧代码。后来的改法：3 轮后要求作者重新考虑方案；后续轮次只审新增的 diff；按类别报 bug，让作者一次修完同类问题。目前还没有"回滚率上升时自动收紧审批"的熔断机制。

**可借鉴：** 分三周落地。

1. **第 1 周：** 选一个仓库开启 AI 审查，写 `REVIEW.md`，PR 模板加上 Testing / Risk / How to revert 三栏。
2. **第 2 周：** 书面定义三档风险，认证、计费、CI、发布等路径用 CODEOWNERS 强制人工审查，新 commit 自动撤销已有审批。
3. **第 3 周：** 把过去半年的事故 PR 做成评测集，审查轮次上限设为 3，开始统计每个 PR 的人工审批数和回滚率。

### 深读｜[The Thin Orchestrator](https://engineering.fb.com/2026/10/19/ml-applications/thin-orchestrator-ai-agent-architecture/)

Meta · 10-19 · 约 8 分钟 · 摘要已足够

**问题：** 推荐系统接入一个新数据列，要跨 3 个仓库、3 种语言、最多 6 个流水线阶段改代码。第一版是一个"什么都懂"的单 agent，demo 能跑，上生产后开始幻觉：知识塞得越多，效果越差，还会把 A 子系统的命名规范用到 B 上。另一种单 agent 方案要工程师为每个任务手写 system prompt，才能有 70% 到 80% 的成功率，不写只有 10% 到 20%。

**方法：**

- 编排层是 1,300 行确定性代码，自己不做任何领域判断，固定走 7 步：读 subagent 说明、查重、收集必填字段、推断仓库类型、可靠性闸门、委派、处理结果。只有"委派"这一步调用 LLM，而且是在上下文隔离的 subagent 里。
- 14 个 subagent 结构统一，都包含：知识源、委派前必须收集的清单、执行步骤、在 monorepo 里查找代码模式的方法、错误到解决方案的映射。
- 用工作流模板组合 subagent，比如 Schema、Validation、Population、Testing 四步串起来。新增"流水线迁移"场景时只写了一个模板，没写新的 agent 代码。
- 25 个以上的知识文件按需加载，更新后下次会话就生效。

**数字：** 新数据列的配置准备，人工需要 3 到 4 天，旧系统约 1 天，现在不到 1 小时。约三分之二的改动不需要大幅人工修改。

**局限：** 没披露样本量，也没定义什么算"大幅修改"；剩下三分之一仍要人工改；正文只列出了 3 个模板。

**可借鉴：** 把"交给哪个 agent、要收集哪些字段、要不要指定 reviewer"这类决策全部写进代码，不让 LLM 判断。领域知识拆成若干几千 token 的小文件，按需加载。新场景先试着用现有 agent 组模板；如果组不出来，说明 agent 和具体用例耦合得太紧。

### 可扫一眼

- [How Meta Built Forum With AI-Native Engineering](https://engineering.fb.com/2026/10/15/ml-applications/how-meta-built-forum-ai-native-engineering/)（Meta，10-15）：一个小团队 8 周做出新 App，功能追平 Facebook Groups，工作方式从"人在每一步里"转向"人在流程之上监督"。
  - 完成的标准是自动化测试和视觉检查都通过。
  - 最常见的失败是 agent 搞错自己在哪个页面。解法不是写说明，而是给它工具，让它直接读模拟器里的实时视图层级。
  - 原型代码放在单独的构建变体里，生产包根本不编译这部分。
  - 同一个错误犯两次以上，就把纠正写成规则。
- [Five months treating bugs like patients…](https://www.cockroachlabs.com/blog/experiment-running-hospital-code/)（Cockroach Labs，上期保留）：5 个月合并 1,238 个 PR，只回滚 7 次，平均每个 issue 约 $84。返工超过 4 到 6 轮就熔断，交给人。可以和 Claude Code 的"3 轮上限"对照着看：两边都发现，agent 互审最大的风险是停不下来。

## 三、社区热点

### 深读｜HN：[How the Claude Code team does code review](https://news.ycombinator.com/item?id=50122951)

482 分、479 条评论 · 精选楼层约 30 分钟 · 摘要已足够

**争论焦点：** 如果没人读代码，审查和"理解"还成立吗？

- **"只适合实验室"（高赞首楼 avinoth）：** 这和当年 Google 的基础设施文章一样，只适合他们自己。Anthropic 的 token 几乎无限，普通团队照抄会形成依赖，还是应该继续读代码。
- **"信任模型变了"（jonahx，被大量引用）：** 已经没有人脑中有系统的因果模型，一切都押在"Claude 总能读懂需要的那片代码"上。一旦这个前提失效就无法恢复，"像拥有一艘看不懂的外星飞船"。
- **"人类代码库本来就这样"（cheema33、dmd）：** 大组织里本来就没人掌握全局，dmd 在银行见过跑了 60 年、从没人完整理解过的代码。反驳者 mqus 回应：那种状态是几年才形成的，LLM 几天就能造出来。
- **算账派（markbao）：** AI 审查每月几千美元；人工审查要占工程师约三分之一的时间，折合每人每年 5 到 10 万美元。
- **合规派（gaal_dornick）：** SOC2 要求每个改动至少有另一个人审过，"作者加 AI"怎么过审？内部人员作恶又怎么防？
- **反例（marcindulak）：** 在 Claude Code 的公开仓库里，维护者贴出一段 Claude 写的讲解，把 issue 自动关闭的规则说错了。可见"让 Claude 写讲解来帮人理解代码"本身也会出错。
- **文风之争：** 不少人认为原文是 AI 写的，有人用 Pangram 检测，结果约 80% 是 AI 文本。

**可借鉴：** 引入"零人工审批"前，先回答三个问题：

1. 合规上，SOC2 或内审允不允许？
2. 问责上，出了问题谁是那个负责的"人"？
3. 理解上，AI 生成的讲解谁来抽查？

建议每周随机抽 5 份 AI 生成的讲解，让 owner 核对。

### 深读｜"手写代码已死"之争：DHH 在 Rails World 的演讲引发连锁讨论

来源：[The Pulse: RoR creator sparks new "death of coding by hand" debate](https://blog.pragmaticengineer.com/the-pulse-ror-creator-sparks-new-death-of-coding-by-hand-debate/)（Gergely Orosz，10-01）· 约 10 分钟 · 摘要已足够

**事件：** DHH 宣布 37signals 已经"放下铅笔"，手写代码成了例外。他的原话是："就像在 Sentry 看到 bug：agent 为什么没做出来？修机器、修工厂。"他把 Opus 4.5 的发布比作这个时代的柯达布朗尼相机（第一款让普通人用得起的相机）。随之而来的变化：后端转向 Rust，重做原生 App，他本人"已经从职业程序员退休"。他认为抽象的价值要重新评估，因为重复的代价已经接近零。

**各方立场：**

- **全面拥抱（DHH）：** 对大多数公司的大多数程序员来说，手写代码已经没有经济价值。Rails 的"约定优于配置"恰好对 agent 友好。
- **一线反弹（匿名大厂工程师 voxium）：** 从 spec、代码、测试到 PRD、工单，全由 Claude Code 生成。团队每天工作 12 到 13 小时"只为按回车"，"没人在思考"。
- **质量警报（Gergely）：** 他在 Uber Eats 新上线的加料选择器里一次就找到 3 个明显 bug，比如"最多可选 999 份"、荷兰语文本溢出。他的建议是：与其每个 PR 都跑昂贵的 AI 审查，不如让 AI 生成确定性的 lint 规则。
- **"是观念，不是模型"（Geoffrey Huntley，[原文](https://ghuntley.com/agency/)）：** 模型早就够用了，DHH 说的时间点只是他自己想通的时候。他认为 skill 包和 `AGENTS.md` 像"软件工程师的星座运势"，读着舒服却不保证有效；应该改用 pre-commit hook 做确定性的架构约束，每隔几个月删掉 skills 重新验证。人只守两头：愿景和验证。代码可以不可读，但必须可解释。
- **反对"认知投降"（Sam Newman，Pragmatic Engineer 播客 10-07）：** AI 本该把人解放出来去思考，现实却是更多的上下文切换和更长的工时。他主张模块边界由人设计，AI 只在边界内自由发挥。

**可借鉴：**

1. 团队里反复出现的 agent 规范问题（比如绕过统一日志库），从 `AGENTS.md` 里的文字规定改成 pre-commit 或 CI 检查，检查失败时把纠正提示返回给 agent。
2. 每个核心模块指定 owner，要求能在白板上讲清楚状态机和边界，作为"不逐行读代码"的前提。

### 可扫一眼

- [Show HN: Parsimony](https://news.ycombinator.com/item?id=50077619)（77 分）：一个衡量模型"写了多少多余代码"的开源基准，统计公开补丁里净增的语句、调用、名称和字面量，删掉的代码会扣分。GPT-6 Astra 排第一，但有人认为它是在"打代码高尔夫"，写出来不可读，宁可要 Claude 那些多余的注释和测试。评论里分享的做法：Opus 写完后，让另一个模型按命名、类型、函数、文件、注释、测试分轮做压缩清理。
- [nobody should type code by hand anymore](https://ghuntley.com/agency/)（Geoffrey Huntley，10-13）：另外三点可以直接用。一是选定一个模型长期用，换模型就像换一个开发者，要重新磨合。二是认真读厂商的模型卡，同一句加重语气的指令，在不同厂商的模型上效果可能正好相反。三是用 Nix 把包括操作系统在内的整个系统纳入测试，再用属性测试验证"只扣款一次"这类不变量。
