# AI Coding 日报 · 2026-10-28（周三）

## 今天动向

1. **用 Manus 改造 Manus：一个人并行推进十几二十个需求。** Manus 联合创始人张涛复盘 AI Native 组织实践：不是把仓库合并成 monorepo，而是用统一入口 + 写给 AI 的 `AGENTS.md` 说明书（Manus-mono），让 AI 跨仓改、本地验、走发布；约一半产品经理能自己写代码上线。代价是曾有一个月人均 AI 开销超 1 万美元。（[小虎解读 / 转载](https://xiaohu.ai/article/manus-ai-native-org/) · [53AI 全文转载](https://www.53ai.com/news/shuziyuangong/2026102760938.html) · 原文公众号「潜云思绪」10-26）
2. **Snowflake 用约 4300 万行的超大 monorepo（非测试源约 1700 万行）做了 SnowPR。** 65 个真实已合 PR 任务，用随 PR 上线的隐藏测试打分；Cortex Code REM 模式在 opus-5 上以最低成本追平顶尖 harness，并解出 62/65。（[Snowflake 工程博客](https://www.snowflake.com/en/blog/engineering/Benchmarking-coding-agents/)）
3. **微软：生成代码变便宜，信任变成稀缺资源。** 从 Windows Clang/LLVM 迁移、静态分析修复，到 C/C++→Rust 与规格驱动验证，核心主张是小专家团队批知识库、agent 规模化落地，人的注意力只花在批准知识和歧义案例上。（[Microsoft Command Line](https://commandline.microsoft.com/agentic-software-engineering-large-scale-code-migration-language-modernization-spec-driven-development/)）
4. **Anthropic：该把子代理折回主循环了。** Applied AI 团队对比多家企业部署后认为，路由/规划/领域子代理常可折成 skills + MCP tools；单 agent + skills 往往质量更好、延迟更低。保留子代理的条件：上下文膨胀可测、需并行新鲜上下文、工具选择冲突。（[claude.com](https://claude.com/resources/articles/building-agents-when-to-fold-subagents-into-your-main-agent-loop)）
5. **OpenAI 用 GPT-6 家族做了 1,400+ 个维护 PR。** Core Experimentation 团队清理死代码与陈旧实验：删超 80 万行；Sol Ultra 在陈旧实验扫描上拿到 Astra Ultra 92% 的发现量，API 成本仅 14%。（[OpenAI Developers](https://developers.openai.com/blog/maintaining-software-with-the-gpt-6-family)）

## 一、行业动向

### 深读｜[Cheap code, precious trust: Code modernization at scale](https://commandline.microsoft.com/agentic-software-engineering-large-scale-code-migration-language-modernization-spec-driven-development/)

Sriram Rajamani、Tim Bozarth（Microsoft CoreAI）· 2026-10-26 · 约 12 分钟 · 摘要已足够

**问题：** Agent 能比人快几个数量级改几亿行代码时，瓶颈不再是「能不能生成」，而是「敢不敢信任」——行为、安全、架构意图如何在大规模改动下被守住。

**方法：**

- **控制流倒置：** 早期是硬编码流水线调用 LLM；到 2025 年 5 月，agent 规划已强过固定管道，团队改为给 agent 造工具，尤其是告诉它「这次改对了没有」的工具。
- **迁移操作系统：** 不把迁移摊给全公司，而由极小专家团队驱动。Agent 从抽样 finding 学出候选知识库 → reviewer agent 按正确性/最小改动/文件惯例/可维护性打分并回写知识库 → **人批准的是知识库，不是每个补丁** → agent 规模化应用；相似修复分组审阅，降低认知负荷。案例：Windows 数亿行加 Clang/LLVM、CodeQL/PREfast/Roslyn 修复、x86→ARM。
- **语言现代化：** C/C++→Rust 的瓶颈从「能编译」(2025.1) →「能跑过测试」(2025.6) →「约 3 万行可手工引导」(2025.9) →「大规模半自动」(2026.2+)。按 **feature（用户可见行为）** 迁移优于逐行翻译；差异测试 + 对 agent 隐瞒的 holdout 测试；近期开始抽形式规格并用 Verus 证明。
- **规格驱动：** 从代码推断 TLA+ 等规格，用 TLC 检查执行轨迹是否被规格接纳；不符时可能是实现缺陷、规格不准或测试无效。目标是工程师批「系统必须满足的性质」，agent 找归纳不变量。

**数字 / 阶段表：** 文中给出 Rust 现代化时间线四档；Windows 迁移量级为「数亿行」。无单一成功率百分比。

**局限：**

- 开篇系列文，偏框架与问题清单，缺少可复现的通过率/回滚率。
- 规格由 AI 从现有代码推断时，可能只刻画「现在做什么」而非「该做什么」——作者自己列为 open question。
- 「工程师是否最终不读代码」仍是开放问题，不是已验证结论。

**可借鉴：**

1. 大迁移先抽「修复知识库 + 评审标准」，人批知识、agent 批量改；新出现的歧义案例再回灌知识库。
2. 现代化按 feature 设验证门，留一批 agent 看不到的 holdout 测试。
3. 把人的注意力预算写成原则：只花在批准知识、歧义 case、验证证据上。

### 可扫一眼

## 二、工程化实践

### 深读｜用 Manus 改造 Manus：AI Native 组织改造的实践和思考 · **必读原文**

张涛（Manus 联合创始人）· 公众号「潜云思绪」2026-10-26 · 约 12 分钟  
中文转载/解读：[53AI](https://www.53ai.com/news/shuziyuangong/2026102760938.html) · [小虎](https://xiaohu.ai/article/manus-ai-native-org/)（含导览摘要；深读以一手/全文转载为准）

**问题：** AI 写得快之后，损耗仍卡在联调与交接；代码散在多仓时，AI 也看不到全局。研发变快后，瓶颈第一次翻到产品经理「给不出足够多高质量需求」。

**方法（Manus-mono，不是把代码合并进一个 monorepo）：**

1. **统一入口 + 写给 AI 的说明书**（如 `AGENTS.md`）：各仓职责、协作规范、发布流程写进工作区；Git worktree 并行推进多需求。
2. **本地验证：** 完整 Manus 可跑在本机，每轮验证从推测试环境的 5–10 分钟降到几秒（AI 常改几十轮）。
3. **权限内读线上日志/配置/异常**，让排查与工程师同视图。
4. **测试环境改动交给 AI；线上由 AI 提申请、人审批。**
5. **端到端：** 测试账号走真实流程（浏览器/模拟器），逐步录屏验收。

需求流转约 7 步，AI 接走其中 5 步；人守「提出需求」与「审批上线」。产品侧：约一半 PM 能独立写到上线；部分需求从 PRD 变成 **产品需求视频（PRV）**，把边界工况演出来。市场侧做「数字同事」：可判断是否打断、可主动提醒进度、甚至给自己提工具需求。组织口号从 Human in the loop 转为 **Human on the loop**。

**数字：**

- 一个工程师常态并行十几、二十个需求。
- 移动端 7 人同时维护 2 产品共 4 个 App，进度与网页版基本同步。
- 曾有一个月人均 AI 开销 >$10,000（少数人单月可达七八万）；负责同事称近半年未听说因合入问题代码导致线上故障（自述，非统计报表）。
- 反例：AI 自动循环跑一个周末，留下 200+ 待决策——「传话可省，判断省不掉」。

**局限：**

- 一手在微信公众号；官网 manus.im/blog 未见同题长文，公开材料以转载/解读为主。
- 成效多为内部自述；人均万美元级支出对非 Agent 公司不可直接照搬。
- Mono 仍在演进，文中承认不少问题未解。

**可借鉴：**

1. 先做「写给 AI 的全局说明书 + 统一工作区入口」，不必先砸 monorepo。
2. 把本地可验证、测试账号走通、上线审批权留人写成硬门槛。
3. 用 PRV/录屏对齐边界，减少文字需求的跨角色理解差。
4. 给「决策队列」设人的容量上限，禁止无上限的周末自动循环。

### 深读｜[SnowPR: Benchmarking Coding Agents on Snowflake's 43-Million-Line Monorepo](https://www.snowflake.com/en/blog/engineering/Benchmarking-coding-agents/) · **必读原文**

Soyoung Yoon 等（Snowflake）· 2026-10-27 · 约 13 分钟

**问题：** 公开基准多来自约几千文件的 Python 项目，且模型越来越被调到这些集合上；无法回答「哪个 agent 在我们每天改的 Java/C++ Bazel monorepo 上更好」。

**方法：**

- **任务来源：** 65 个真实已合 PR（11 个产品面；62 个来自 monorepo，3 个 Go 工具仓）。Agent 只拿变更前代码与任务描述；随 PR 上线的隐藏测试 + 自有 Bazel/远程 build farm 判分。
- **硬化流水线：** LLM 法官先筛（最大一轮：13,965→4,218→再收窄），人工作者验证；每任务需足够新行为与回归用例、有真修复则过/空改则挂、11 项自动检查 + 对抗评审。除描述外均可脚本化，可跟 CI。
- **对照 harness：** Cortex Code code mode vs REM（把 file/shell/SQL 暴露成单一 REPL 内的 Python 函数；**目前仅内部**）、Claude Code、Cursor、Codex；同模型多 harness，每任务 3 次。

**数字：**

- Monorepo：约 4,300 万行；非测试源约 6.3 万文件 / 1,700 万行。相对 SWE-bench 平均仓：文件约 21×、行数约 39×。参考修复平均 4.0 文件 / 262 行（SWE-bench 约 1.7 / 33）。
- 全库隐藏测试合计：147 个 Bazel target，676 新行为 + 2,890 回归用例。
- opus-5：四 harness pass 率约 84.1%–85.1%（65 题分不出差距），差在成本——REM $6.34/试、Claude Code $6.51、Cursor $6.93、code mode $8.19；REM 解出最多任务 62/65，比 code mode 便宜约 23%。
- haiku-5.5 + REM：70.8% 试次通过、$0.24/试，高于 Claude Code 的 64.1%/$0.26。
- 跨 Java+C++ 任务试次通过约 55%，纯 Java 约 80%；改 ≥3 源文件 70% vs 1–2 文件 89%。
- 描述质量也是测量的一部分：同一隐藏测试下，两名工程师写的描述让 10 个 agent 试次通过率从 83% 掉到 57%。

**局限：**

- REM 不对客户开放；65 题只能分出「档位」，难分细小百分点。
- 端到端 Snowfort 等约四分之一带测 PR 尚无法在任务容器拉起。
- LLM 法官预测通过率与实测相关很弱（Spearman +0.18），只能当过滤器。

**可借鉴：**

1. 用「自家已合 PR + 随 PR 隐藏测试」做私有 agent 榜，而不是只看 SWE-bench。
2. 建题时强制：真修复过、空改挂、回归下限、对抗评审；描述由人写并抽检。
3. 选型时同时报 pass@1/pass@3 与单次成本；同模型换 harness 往往分差不大、账单差很大。

### 深读｜[Building agents: When to fold subagents into your main agent loop](https://claude.com/resources/articles/building-agents-when-to-fold-subagents-into-your-main-agent-loop)

Diane Sarkis（Anthropic）· 2026-10-22 · 约 18 分钟

**问题：** 企业常按组织架构复制出「每团队一个子代理 + 中央编排」，带来上下文丢失、子代理膨胀、Frankenprompt、局部 eval、以及约 2× 的延迟。

**方法：**

- **何时保留子代理：** 单循环因上下文膨胀可测地变差；需要可丢弃的并行新鲜窗口；单 agent 选工具失败或系统提示冲突。
- **目标形态：** 一个模型、一个上下文、开放工具循环；计划写在上下文里并由同一模型修订；领域流程进 **skills**，硬限制与实时数据进 **tools**（按用户意图分组，避免 30–50+ 工具定义挤进系统提示）。
- **迁移步骤：** 先建共享端到端 eval（哪怕 10 条黄金例）→ 先把子代理当 tool 调用拿基线 → 再逐个把 prompt 折成 skill、API 折成 MCP → 只在折后更差时保留子代理。提供 migration kit（build-eval / prompt-audit / hillclimb / cost-optimize）。
- 文中称 Claude Code 对更强模型把系统提示砍了 **80%+**（含渐进披露 skills/tools）。

**局限：** 企业案例多为定性；「2× 更快」来自单一客户对照。折子代理可能打掉原先靠分工兜住的流程（文中 support agent 例子：折完后主 agent 自己回订单而不问物流日期）。

**可借鉴：**

1. 先写端到端任务完成 eval，再谈架构。
2. 按「共享上下文 / 常串联调用」的子代理优先合并。
3. 工具按意图聚合 + deferred tool search；权限检查放进 tool 返回可读拒绝。

## 三、社区热点

### 深读｜[PAUSE: Search-Free Steering of Coding Agents Before Their First Source-Code Edit](https://arxiv.org/html/2610.29870)

Viral Patel、Boyin Tan、Jason Xue、Youcheng Sun（MBZUAI）· arXiv 2610.29870 · 正文长文约 40+ 分钟 · 摘要 + 关键表已通读

**问题：** Coding agent 常把大量步数花在探索与复现上，却在首次改源码时走偏。周期性 oversight（SICA）贵；等行为异常再介入（LivePlan）又可能漏掉「流程整齐但方向错了」的轨迹。

**方法：** 经验上，首次针对源码的 file-editor 请求中位出现在轨迹进度约 **60%**。PAUSE 在**执行该编辑前**拦截一次，用独立 Planner 读任务 + 编辑前 transcript，生成一条自然语言修复计划，同一 Executor 保留上下文与工作区继续。无需学习式 monitor、无需搜索检查点——作者称为 search-free。支持在线转向与离线从失败前缀恢复。

**数字（Qwen3-coder + GPT-5.6 Sol Planner，除非另注）：**

- SWE-agent 在线：Verified 50.2%→65.0%（+14.8）；Multilingual 28.3%→43.0%（+14.7）。
- 对比 LivePlan：Verified 再高 3.2 点、Multilingual 再高 3.7 点，Planner 成本相近。
- 对比 SICA：Verified 低 2.6 点（不显著），Planner 成本约 SICA 的 11%；Multilingual 约 15%。
- OpenHands 在线 +16.8 点（45.4%→62.2%）。
- 离线：Eligible 失败 Verified 223 题中恢复 79（35.4%）；相对 restart，resume 少用 33–41% Executor token。

**局限：** 依赖「首次源码编辑」可拦截；若用 shell 改源码可能漏触发。Planner 不能自己探仓。单次计划不会随新观测刷新。离线恢复要求可忠实还原的 checkpoint。

**可借鉴：**

1. 在 harness 里对「首次改业务源码」设人工/规划闸门，而不是固定每 N 步审一次。
2. 失败轨迹保留调查前缀再续跑，往往比整单重开更省。
3. 内部对照时把 Planner 成本与 Executor token 分开记账。

### 深读｜[AI Promised Less Work. I Have Never Worked More.](https://oioannou.com/blog/ai-promised-less-work/)

Orestis Ioannou（Bold.org VP of Technology）· 2026-10-27 · 约 10 分钟

**问题：** Agent 让「以前不值得做的事」变得值得做，负载从「每周两三个重任务」变成「多个 agent 并行，每个偶尔要你决策」——累的是上下文切换，不是单任务难度。

**数据（作者 GitHub contribution，含私有，非价值度量）：**

- 2026 截至 10-27 已 2,102 次贡献，超过 2021–2025 任一年全年；接近全职写码的 2020（同期 2,371）。
- 2026-08 单月 427，为 2019 至今最高（此前峰值 2020-04 的 319）。
- 工作日中位贡献从 2022–2025 的 3–4 回到到 7（2020 为 8）；≥24 贡献的「重日」2026 已有 16 天。
- 角色已是 VP，图谱却回到全栈高峰——因为实现变便宜后自我加单。节奏呈爆发→回落循环，低谷月仍常高于 Principal 时期均值（约 114/月）。

**局限：** 单人样本；contribution 混合 commit/PR/review/issue。作者声明 AI 协助拉数与起草，观点为自己的。

**可借鉴：**

1. 给并行 agent 数和「待人决策队列」设硬上限（对照 Manus 周末 200+ 决策的反例）。

3. 承认低谷不再低：即使「轻松周」也要预留审 diff / 批计划的注意力。
